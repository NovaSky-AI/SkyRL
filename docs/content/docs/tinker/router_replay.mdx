---
title: "Rollout Routing Replay (R3)"
---

Rollout Routing Replay (R3) stabilizes RL training of Mixture-of-Experts (MoE) models by making the training forward pass activate the **same experts** the inference engine chose during rollout. See [Stabilizing MoE Reinforcement Learning by Aligning Training and Inference Routers](https://arxiv.org/abs/2510.11370) (Ma et al., 2025).

## Why it matters

An MoE router picks the top-k experts per token from router logits. Because the inference engine (vLLM) and the training engine (Megatron) compute those logits with different kernels, the two disagree on expert selection for a meaningful fraction of tokens — even with identical weights. Different experts means different outputs, which shows up as a large training-vs-rollout logprob gap. On MoE models this gap is severe enough to destabilize RL and, in the worst case, collapse training.

R3 records the routing decisions vLLM made during generation and replays them in the Megatron forward. The router logits are still computed normally (so gradients still flow to the router), but the top-k **selection** is forced to match inference. This is exactly aligned with importance-sampling / off-policy corrections like [TIS](/docs/algorithms/off_policy_correction): R3 removes the routing-driven component of the mismatch, and TIS can still correct the residual kernel-level differences.

R3 is only relevant for MoE models. It is a no-op for dense models.

## Enabling R3 through the Tinker API

R3 is supported for the **Megatron** backend of the Tinker server. Enable it with a single backend-config flag; SkyRL automatically turns on routed-experts capture in the inference engine to match:

```bash
--backend-config '{
  ...,
  "trainer.strategy": "megatron",
  "trainer.policy.megatron_config.moe_enable_routing_replay": true
}'
```

Setting `moe_enable_routing_replay=true` implies `generator.inference_engine.enable_return_routed_experts=true`; you do not need to set the latter yourself.

## Client flow

With R3 enabled server-side, `sample` responses carry the per-token expert selections, and you feed them back on `forward_backward`:

1. **Sample.** Each returned sequence includes a `routed_experts` field of shape `[num_tokens - 1, num_layers, top_k]` (routing for every forwarded token; the last sampled token has no routing).
2. **Assemble the datum.** Concatenate the prompt routing and the generation routing to cover `model_input` (i.e. `prompt + response[:-1]`), then pass it in `loss_fn_inputs["routed_experts"]` as a flat tensor whose `shape` is `[seq_len, num_layers, top_k]`. This is exactly what `tinker.types.TensorData.from_torch(routed_experts_tensor)` produces.
3. **forward_backward.** The Megatron backend rebuilds the routing tensor and replays it during the forward/backward pass.

```python
import torch
from tinker import types
from tinker.types.tensor_data import TensorData

# `routed_experts` from a sampled sequence, shape [seq_len, num_layers, top_k]
routed = torch.tensor(sampled_sequence.routed_experts, dtype=torch.int64)

datum = types.Datum(
    model_input=types.ModelInput.from_ints(prompt_tokens + response_tokens[:-1]),
    loss_fn_inputs={
        "target_tokens": TensorData.from_torch(torch.tensor(response_tokens)),
        "weights": TensorData.from_torch(torch.ones(len(response_tokens))),
        "logprobs": TensorData.from_torch(torch.tensor(old_logprobs)),
        "advantages": TensorData.from_torch(torch.tensor(advantages)),
        # R3: replay the rollout routing during training.
        "routed_experts": TensorData.from_torch(routed),
    },
)
```

If `routed_experts` is omitted from a datum, that datum falls back to Megatron's own routing (equivalent to R3 off), so you can mix R3 and non-R3 data.

## Verifying the effect

The metric to watch is the training-vs-rollout logprob mismatch (e.g. mean `|rollout_logprob - training_logprob|` over response tokens). With R3 on, it should drop substantially versus a matched R3-off run on the same MoE model. The GPU test at `tests/backends/skyrl_train/gpu/gpu_ci/megatron/test_router_replay_tinker_qwen36.py` asserts this on `Qwen/Qwen3.6-35B-A3B`.

## Notes and limitations

- Supported for Megatron MoE policies with vLLM rollout generation. Dense models and other backends ignore the flag.
- R3 is wired end-to-end for both the colocated (in-engine sampling) and non-colocated (forwarded sampling) Tinker paths.
- Routing payloads add transport overhead proportional to `num_layers * top_k` per token; this is expected and does not affect training speed materially.
