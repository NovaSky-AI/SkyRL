# GLM 5.3 on B300: native SkyRL examples

Three review candidates for the SkyRL Tinker-compatible API. No TCLI imports, scheduler,
Kubernetes manifests, private registry or bootstrap patches.

| Profile | Trainer: nodes / TP / CP / PP / EP | Inference | Context | Evidence boundary |
| --- | --- | --- | --- | --- |
| 32k-2n | 1 / 8 / 1 / 1 / 8 | 1 node, TP8 | 32,768 | Prior mechanics evidence; latency and stricter numerical qualification remain open |
| 256k-2n | 1 / 4 / 2 / 1 / 8 | 1 node, TP8 | 262,144 | Canonical memory baseline, not the later MLP/offload diagnostics; exact-context memory qualification remains open |
| 256k-3n | 2 / 8 / 1 / 2 / 8 | 1 node, TP8 | 262,144 | PP2, 38/40 layers; post-update numerical discrepancy remains unresolved |

Eight B300 GPUs per node. Official BF16 model weights, rank/alpha 32, shared expert adapters,
all listed attention/MLP targets, default FP32 publication and MTP disabled. KV cache remains
explicitly FP8; BF16 model weights do not mean every tensor/cache is BF16.
No BF16-publication override, attention-only adapter or private diagnostic kernel is imported.

The 32K profile explicitly uses max_num_seqs=16 as a serving candidate, not a throughput
guarantee. Other profiles use 8. These are sequences within one TP8 engine, not engine counts.
The 32K 16,384-token pack budget is a soft bin target, not its context limit.
The API connection ceiling of 512 is not a recommendation to submit 512 simultaneous trajectories.

## Run

Use identical SkyRL checkout/environment on every node and an already-owned Ray cluster.
This PR ports settings to current main, NOT the historical binary environments: its base
uses Torch 2.13; the previous deployments used Torch 2.11. No dependency pins are changed here.

Download the same pinned checkpoint to an identical path accessible on every node:

```bash
hf download zai-org/GLM-5.3-BF16 --revision 304b8051cfb2b260b61ce0cbe330e02a98e73639 \
  --local-dir /shared/models/glm53-bf16
```

Start Ray on the head with `ray start --head --port=6379 --num-gpus=8`;
join each worker with `ray start --address=HEAD_IP:6379 --num-gpus=8`.
Use two total nodes for 2n or three for 3n. Do not join a shared production cluster.
Verify Ray places trainer and inference on separate physical nodes.

```bash
export RAY_ADDRESS=auto
uv run --isolated --extra tinker --extra megatron examples/tinker/glm53/run_server.py 256k-3n \
  --model-path /shared/models/glm53-bf16 --state-dir /shared/glm53-256k-3n \
  --database-path /local/glm53-256k-3n/tinker.db
```

Add --print-config for a CPU-only dry run. The server binds localhost; remote clients need
approved authenticated transport. Request a rank-32 adapter using the same model path as the
API's base-model name. This starts a service, not a training job or a new cluster.

Use one state directory per service. LoRA/checkpoint paths must be shared consistently;
keep the separate SQLite database on the API head's local disk. Put compilation caches on node-local scratch,
not shared storage, before starting Ray. For comparisons with previous deployments preserve
NVTE_FLASH_ATTN=0, NVTE_FUSED_ATTN=1, NCCL_NVLS_ENABLE=0 and
VLLM_ALLREDUCE_USE_SYMM_MEM=0; network interface names are fleet-specific.
Upstream session cleanup stays enabled; the owner remains responsible for bounded teardown.
