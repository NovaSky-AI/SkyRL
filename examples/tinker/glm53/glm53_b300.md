# GLM 5.3 on B300: native SkyRL examples

Three review candidates for the SkyRL Tinker-compatible API. No TCLI imports, scheduler,
Kubernetes manifests, private registry or bootstrap patches.

| Profile | Trainer: nodes / TP / CP / PP / EP | Inference | Context | Evidence boundary |
| --- | --- | --- | --- | --- |
| 32k-2n | 1 / 8 / 1 / 1 / 8 | 1 node, TP8 | 32,768 | Prior mechanics evidence; latency and stricter numerical qualification remain open |
| 256k-2n | 1 / 4 / 2 / 1 / 8 | 1 node, TP8 | 262,144 | Canonical memory baseline, not the later MLP/offload diagnostics; exact-context memory qualification remains open |
| 256k-3n | 2 / 8 / 1 / 2 / 8 | 1 node, TP8 | 262,144 | PP2, 38/40 layers; post-update numerical discrepancy remains unresolved |

Eight B300 GPUs per node. Official BF16 model weights, rank/alpha 32, shared expert adapters,
all listed attention/MLP targets, default FP32 publication and MTP disabled. Inference explicitly
uses `model_dtype=bfloat16` and `kv_cache_dtype=auto`, so KV follows BF16, not FP8.
vLLM discovers its LoRA target modules from the exported adapter; the trainer's targets are unchanged.
No BF16-publication override, attention-only adapter or private diagnostic kernel is imported.

The profiles do not override `max_num_seqs`. This source's SkyRL default is 1024; that is a
scheduler ceiling, not a guarantee that 1024 full-context sequences fit or run concurrently.
Record effective KV capacity, admitted sequences and preemptions before throughput testing.
The 32K 16,384-token pack budget is a soft bin target, not its context limit.
The API connection ceiling of 512 is not a recommendation to submit 512 simultaneous trajectories.

## Run

Use identical SkyRL checkout/environment on every node and an already-owned Ray cluster.
This PR ports settings to current main, NOT the historical binary environments: its base
uses Torch 2.13; the previous deployments used Torch 2.11. No dependency pins are changed here.

Download the same pinned checkpoint to an identical path accessible on every node:

```bash
hf download zai-org/GLM-5.3-BF16 --revision 304b8051cfb2b260b61ce0cbe330e02a98e73639 \
  --local-dir /shared/models/glm53-bf16
```

Start Ray on the head with `ray start --head --port=6379 --num-gpus=8`;
join each worker with `ray start --address=HEAD_IP:6379 --num-gpus=8`.
Use two total nodes for 2n or three for 3n. Do not join a shared production cluster.
Verify Ray places trainer and inference on separate physical nodes.

```bash
export RAY_ADDRESS=auto
uv run --isolated --extra tinker --extra megatron examples/tinker/glm53/run_server.py 32k-2n \
  --model-path /shared/models/glm53-bf16 --state-dir /shared/glm53-32k-control \
  --database-path /local/glm53-32k-control/tinker.db
```

Add --print-config for a CPU-only dry run. The server binds localhost; remote clients need
approved authenticated transport. Request a rank-32 adapter using the same model path as the
API's base-model name. This starts a service, not a training job or a new cluster.

Use one state directory per service. LoRA/checkpoint paths must be shared consistently;
keep the separate SQLite database on the API head's local disk. Put compilation caches on node-local scratch,
not shared storage, before starting Ray. For comparisons with previous deployments preserve
NVTE_FLASH_ATTN=0, NVTE_FUSED_ATTN=1, NCCL_NVLS_ENABLE=0 and
VLLM_ALLREDUCE_USE_SYMM_MEM=0; network interface names are fleet-specific.
Upstream session cleanup stays enabled; the owner remains responsible for bounded teardown.

## Fixed-input client: review before launching

`run_client.py` follows the bounded, synthetic full-context approach from
`examples/train_scripts/full_context`, without a dataset or task rollout collection.
It trains with **GSPO on two built-in deterministic token fixtures**, each repeated to the full
context. One has sequence-constant advantage +1, the other -1; their tokens differ so the
updates do not cancel by construction. Every input position has a shifted target and unit mask.
These synthetic advantages exercise RL mechanics, not meaningful reward learning.

Default flow: fresh rank-32 adapter → three optimizer steps, each with two accumulated
full-context backwards → ephemeral publication and a short sample after each update →
durable checkpoint → unload this adapter. Each backward scores exactly 32,768 positions;
the short sample does **not** prove full-context inference or rollout concurrency.

Before each update, score both fixtures with `trainer.forward` and freeze those old-policy
logprobs for its two backwards. Recompute them only after the optimizer, for the next update.
The `cross_entropy` label appears only on **forward-only scoring**, never `forward_backward`.
GSPO uses the server's clipping defaults (0.2 below/above at this base) and the profile's
`sequence_mean` reduction. Ratios should start near one; this is not a clipping-edge-case test.
References come from the trainer, not vLLM: reported rollout-logprob-gap metrics here do not
establish train/sampler parity. That and real-task learning remain downstream qualification.

```bash
timeout --signal=TERM --kill-after=30s 2h \
  uv run --isolated --extra tinker examples/tinker/glm53/run_client.py \
  --model-path /shared/models/glm53-bf16 \
  --context 32768 --batch-size 1 --steps 3 \
  --output-dir /local/glm53/control-01 > /local/glm53/control-01.log 2>&1
```

Use an existing parent directory for log redirection and a new output directory per run.
The fixtures are deliberately synthetic. A different fixture is a different workload;
do not compare unlike inputs as an optimization. No Tau/GSM8K dependency is needed.

Outputs: `datums.json` (exact input/target/mask fixtures), `run.json` (model/SDK/settings/hash),
`step_*_batch_*.json` (complete replay inputs, including computed old logprobs and advantages),
`phases.jsonl` (reference forwards, backwards, optimizer, publication/sample and checkpoint timing).
Keep the rendered server config, image digest, source/package pins and server logs alongside
these files. Client times include RPC/queue overhead. First publication includes lazy inference
bring-up when applicable; later publications measure replacement. No internal serialization/
loading split or vLLM GPU trace is claimed by these client timings.

The client unloads only the adapter it creates. SkyRL's default warm-runtime behavior keeps
the underlying service up for reuse. A shell timeout/process kill can interrupt cleanup:
inspect the recorded model ID and pending work before reuse; client exit does not free the nodes.

### Paired profiler run

First measure the unprofiled control above. For a separate profiled service, add
`--profile-dir /local/glm53/traces/profile-01` to `run_server.py` (or inspect with `--print-config`).
Use the same model, text, shapes, learning rate and step count; a new service/state directory
keeps the profiler schedule comparable. Do not modify a live shared service.

This PR connects the existing policy-worker profiler to Tinker: start once when the policy
runtime is created, advance after each policy optimizer step, stop at runtime teardown.
Rank 0 warms up through the first optimizer and records one window through the second.
That window includes the intervening policy-side publication work, next reference forwards
and both second-step backwards. Other adapters share that schedule, so use a dedicated single-client baseline.

CPU/CUDA Chrome traces include tensor shapes and memory on **policy rank 0 only**.
They do not profile vLLM's worker processes, prove all-rank memory headroom or record initial
model loading. Exported traces must actually exist before profiling is called successful.
Profiling can retain tensors and add overhead: profile timings/OOMs are not the unprofiled
control. Use traces to pick one candidate, then compare equal-work unprofiled runs.
